# SAT vesting + staking security audit

**Date:** 2026-11-14  
**Auditor:** Cursor cloud agent (source review + local CDT 4.1.1 / Spring 1.2.2 tests; no signing, no deployment, no private keys)  
**Code under review:** `smartavest/` (planned `smartavest11`), `smartastake/` (planned `smartastake1`), interaction with live `sat.token` (`sattoken1111`) and `leeftrader` (`smartatrader`) including the `setgov` / `binary_extension<name> gov` patch in `smartastake/docs/TRADER_PATCH.md` and `docs/*.md`  
**Launch plan:** [docs/README.md](docs/README.md) batches B0–B6 and the approved governance numbers (proposal 10k SAT, quorum 10%, approval 50%, vote 3d, timelock 2d, unstake cooldown 7d adjustable 3–30, guardian `smartaadmin1`, `sat_lp_fee_share` 50%, buyback 0)

This is a human-style source-and-test review of the **new, undeployed** contracts. It is not a substitute for a specialist Antelope firm. Live `sattoken1111` / `smartatrader` findings from [AUDIT-REPORT.md](AUDIT-REPORT.md) (2026-11-09) still apply to those accounts; this PR does **not** change their WASM.

No secrets or private keys were used or added.

---

## Verdict

No path was found for an unprivileged user to mint SAT, drain the vesting vault to a non-beneficiary, steal another staker's principal, or bypass airdrop 25% / 30-day caps. Fake-token `get_first_receiver` checks, self-transfer ignores, claim-before-transfer ordering, and Synthetix-style reward-per-token math held up under review and local tests.

Two **High** stake-contract bugs were exploitable before this PR:

1. A permissionless vest claim while `total_staked == 0` parked the SAT in the reward pot; the first 0.0001 SAT staker took all of it.
2. A passed vote that nobody `queue`d stayed `ST_ACTIVE` forever. Queueing it later started a **fresh** timelock, so a stale `setsplit` / `setlimits` / `setcooldown` could override a newer executed decision after the 14-day queued-only grace from PR #5.

Those, plus Medium issues (proposer not locked, dummy airdrop slot grief, `require_auth` any permission on admin/guardian, stake rows never erased), are fixed in `smartastake` on this branch. `smartavest` needed no code change (wasm hash unchanged). `leeftrader.cpp` and `sat.token/` were not modified.

**Do not treat this as a firm audit.** Guardian veto remains a v1 centralization backstop. Just-in-time staking of reward lumps, mid-stream vest top-ups, and a rejecting beneficiary still behave as designed (documented, not changed). Live admin-key / 80M mint risk on `sattoken1111` is unchanged.

## High

### H-01 First staker captures parked rewards

**Location:** `smartastake.cpp` `fund_reward` / `flush` / `credit_stake` (pre-fix); vest `claim` is permissionless and pays `smartastake1` with memo `vesting claim`.

**Impact:** While `total_staked == 0`, incoming SAT (vest claims, `reward` memo, funder forwards, trader payouts) was held in `reward_pending_undistributed`. The first stake — even `0.0001 SAT` — flushed that pot onto its reward-per-token snapshot. A sniper watching a permissionless `smartavest::claim` of the 23.75M rewards stream could take the whole lump. Launch B2 (stake `smartadrop11` first) was only operational.

**Exploit sketch:**

1. After B1, before B2, anyone calls `smartavest::claim` on the rewards stream (or a funder sends SAT).
2. Attacker transfers `0.0001 SAT` to `smartastake1` with memo `stake`.
3. Attacker `claim`s; the parked SAT is theirs. Unstake + cooldown (3–7 days) and leave.

Reproduction: `integration/drive.py` previously labelled this `FINDING` S-1 (mallory staked 1 unit and took the vest lump). After the fix it is `FIXED`.

**Fix (this PR):** `fund_reward` requires the configured `airdrop_account` to already have `amount > 0` (`fund not staked`). Vest claims, funder memos, trader payouts, and `reward` transfers revert until B2. The fund's own `stake` transfer is `credit_stake`, so B2 still works. If `airdrop_account` is empty (no fund), the old hold-and-flush path remains.

Tests: `smartastake/tests/drive.py` (reward reverts, then fund-first; tiny staker cannot claim the fund-era lump); `integration/drive.py` S-1.

### H-02 Unqueued proposals never expire; delayed queue refreshes timelock

**Location:** `smartastake.cpp` `queue` (pre-fix `eta = now + applied_timelock`; no expiry of `ST_ACTIVE`). PR #5 only expired **queued** proposals 14 days after `eta`.

**Impact:** A passed `setsplit` / `setlimits` / `setcooldown` that nobody queued stayed `ST_ACTIVE` indefinitely. Calling `queue` months later set `eta = now + timelock`, i.e. a **new** 2-day window, and `execute` would apply the stale payload and override a newer executed vote. That is a timelock bypass and a governance rewrite. Guardian veto only worked on `ST_QUEUED`, so a pocketed vote was invisible until the surprise queue.

**Exploit sketch:**

1. Pass proposal A (e.g. `setcooldown` 5 days). Do **not** queue it.
2. Later, pass and execute proposal B (cooldown 2 days). Current config is B.
3. Queue A. It becomes queued with a fresh `eta`. After 2 days, execute A. Config reverts to 5 days.
4. Same pattern for `setsplit` / `setlimits` against `smartatrader` after `setgov`.

**Fix (this PR):**

- `eta = end_time + applied_timelock` (clock starts when voting ends).
- `queue` of an `ST_ACTIVE` row with `now > eta + 14 days` marks it `ST_EXPIRED` (status 6) and frees an airdrop slot if needed.
- Immediate queue after `end_time` is unchanged (`eta` equals the old `now + timelock` in that case).

Tests: `drive.py` unqueued expiry; `integration/drive.py` S-5 (`FIXED`). S-4 (queued expiry from PR #5) still holds.

## Medium

### M-01 Proposer not locked; dummy airdrop slot grief

**Location:** `propose` (no `vote_lock_until`); `veto` (pre-fix `ST_QUEUED` only); `open_airdrop_id` set at propose.

**Impact:** 10,000 SAT (the proposal threshold) was enough to:

- Inflate `snapshot_total` and unstake immediately (proposer was not vote-locked), making quorum harder for everyone else.
- Open a dummy `airdrop` and block `open_airdrop_id` for the 7-day vote. After anyone `queue`s it as defeated (0 votes), repeat. Serial grief of the airdrop slot at no extra lockup.

**Fix (this PR):** `propose` sets `vote_lock_until` to at least `end_time` (same as voting). `veto` accepts `ST_ACTIVE` or `ST_QUEUED` and always clears `open_airdrop_id` for an airdrop. Guardian can kill a dummy in-flight airdrop immediately.

Tests: proposer unstake fails with `vote locked`; veto of active and queued airdrops clears the slot.

### M-02 `require_auth` any permission on admin / guardian

**Location:** `setfunder`, `veto` (pre-fix `require_auth(admin)` / `require_auth(guardian)`).

**Impact:** Same class as [AUDIT-REPORT.md C-02](AUDIT-REPORT.md#c-02-require_auth-any-permission-bypasses-intended-roles). `require_auth(name)` succeeds if **any** permission of that account is in the authorization list. `smartaadmin1@owner` (historically a weaker or single-signer layout) could `setfunder` / `veto` without the advertised `@active` 2-of-3.

User actions (`unstake`, `withdraw`, `claim`, `propose`, `vote`, `claimdrop`) still use `require_auth(owner)` — standard for “this account”, and not a role bypass.

**Fix (this PR):** `require_auth(permission_level{admin, "active"_n})` and the same for `guardian`. ABI unchanged. Test: `veto` with `guardian@owner` fails `missing authority`.

This PR does **not** change `leeftrader` / `sat.token` `require_auth` (existing audited contracts).

---

### M-03 Stake rows never erased; contract pays RAM

**Location:** `credit_stake` `stakes.emplace(get_self(), …)`; no `erase`.

**Impact:** Notify handlers cannot bill another account, so the contract pays RAM for every first-time staker. Rows survived full unstake + withdraw. Many tiny accounts can consume contract RAM (each new WAX account is the expensive part; the row is hundreds of bytes). Documented as a known limit.

**Fix (this PR):** After `withdraw` and `claim`, if `amount == 0`, `unstake_amount == 0`, and `pending_rewards == 0`, erase the row (RAM returns to the contract). Residual: a live 1-unit stake still occupies a contract-paid row until it fully exits. No minimum-stake was added (would change product numbers).

Test: after full unstake + withdraw with no pending, `"alice" not in stakes`.

### M-04 Just-in-time staking of reward lumps

**Location:** `fund_reward` distributes `qty * SCALE / total_staked` immediately. `reward_rate` / `reward_period_secs` are stored only.

**Impact:** A staker who joins immediately before a large vest claim or trader payout receives a pro-rata share and can leave after the cooldown (7 days at launch, votable 3–30). Not theft of someone else's already-settled rewards (late staker `paid` is the current accumulator). Integration S-2: mallory took 22.4615 of 100 SAT in the local mix.

**Fix:** Not in v1. Operational: prefer many small vest claims. Streaming is a v2 item. Guardian / cooldown bound the grief.

---

### M-05 Mid-stream `fund:<id>` vests pro-rata immediately

**Location:** `smartavest.cpp` `ontransfer` `fund:` increases `total`; `compute_vested` uses the new total.

**Impact:** Funding a stream at 50% elapsed makes 50% of the top-up immediately claimable. Intended if you want to “catch up”; surprising if you meant the new SAT to vest from zero. Launch B4 funds fully at open.

**Fix:** None (design). Do not top up mid-stream unless that effect is intended. Integration V-3 kept as `FINDING`.

---

### M-06 Rejecting beneficiary bricks the stream

**Location:** Vest `claim` always transfers to the fixed beneficiary. No `setbeneficiary` / `withdraw`.

**Impact:** A contract that rejects SAT (or `smartastake1` before `setfunder`) reverts every claim. SAT stays in the vault, unclaimable, forever. Hostile/buggy beneficiary cannot drain the vault (claimed is only updated if the transfer succeeds, because the inline failure rolls the tx back).

**Fix:** None in WASM (immutability is the point). Ops: B3 `setfunder` **before** any rewards-stream claim and before retiring the stake admin. Integration I-1 / V-2 kept as `FINDING`.

---

### M-07 Unclaimed airdrop liability never expires

**Location:** `execute` of `airdrop` moves SAT from the fund into `airdrop_liability` + `drops`. `claimdrop` is the only exit. No sweep.

**Impact:** Recipients who lose the proof, or a tree that includes dead accounts, leave SAT in the contract indefinitely. The 25% cap is on the fund's **staked** balance at propose/execute, so repeated unclaimed drops shrink what future airdrops can pay from, but they do not steal user stakes.

**Fix:** Not in v1. Guardian should reject dishonest or un-claimable trees during the 48h timelock.

## Low

### L-01 Empty memo stakes

Memo `stake` **or empty** credits principal. An accidental SAT transfer to `smartastake1` locks the sender into cooldown. `reward` is the explicit donation memo. Not changed.

### L-02 Unstake resets the whole cooling timer

Documented. A second `unstake` sets `unstake_ready = now + cooldown_secs` for the **entire** cooling balance. Self-grief only (`require_auth(owner)`). Tests cover it.

### L-03 Reward dust locked in the pot

`muldiv` truncates toward zero. Dust stays in `reward_pot`. There is no `rescue`. At SAT scale this is tiny per distribution; over many rounds it can accumulate. Invariant is `balance >= liabilities` (dust makes `>`).

### L-04 uint32 time near year 2106

`unstake_ready = now + cooldown_secs` and `end_time = now + vote_secs` are uint32. Near 2106 they can wrap so `withdraw` / `queue` succeed early. Vesting already rejects schedules that overflow uint32. Same class as trader `lock_secs`. Not worth a table change for v1.

### L-05 `init` does not `is_account` some names

Stake `init` requires non-zero `admin` / `guardian` / `token_contract` / `trader` but does not call `is_account`. Vest `init` does. A mistyped trader makes later `setsplit` execute fail. Operator error at B1.

## Info

### I-01 Controls that work

**Auth (after this PR):**

| Action | Auth |
|---|---|
| `smartavest::init` | `self` |
| `openstream` / memo `open:` | `config.admin` / `from == admin` |
| `claim` | none; always pays beneficiary |
| `fund:` | anyone (increases `total` only) |
| `smartastake::init` | `self` |
| `setfunder` | `cfg.admin@active` |
| `unstake` / `withdraw` / `claim` / `propose` / `vote` / `claimdrop` | the named account |
| `compound` / `queue` / `execute` | permissionless (compound is fund-only) |
| `veto` | `cfg.guardian@active` |
| log actions | `self` |
| airdrop fund `unstake`/`withdraw`/`claim`/`vote`/`propose` | rejected (`proposal-only` / `no voting power`) even if a key can still sign |

**Notify:** both contracts use `on_notify("*::transfer")`, ignore `to != self` and `from == self`, then `check(get_first_receiver() == cfg.token_contract)` and `symbol == 4,SAT`. Fake SAT from `bad.token` reverts. Wrong precision reverts. Vest unknown memos revert (SAT cannot sit outside a stream). Stake unknown memos revert unless `from` is a funder or the trader (always reward) or memo is `stake` / empty / `reward`.

**`sat.token` notify order:** `require_recipient` is registered before balance updates; Antelope runs notifies after the action body, so stake/vest see the credited balance. `from != to` makes self-transfers impossible at the token layer.

**Reentrancy:** vest updates `claimed` before the inline transfer. Stake zeros pending / cooling / drop claims before `send_sat`. A beneficiary `on_notify` that re-enters `claim` hits `nothing to claim` and rolls the whole tx if it `check`s.

**Reward math:** `muldiv` is 256-bit `(a*b)/den`, truncation toward zero. Host test + 75/25-style floor shares in the suite. First-staker flush after this PR cannot fire against a configured fund that is not yet staked (H-01). Late stakers get `paid = current acc` and do not steal prior rewards.

**Airdrop:** 25% of **compounded** fund stake at propose **and** execute; 30-day gap from `last_airdrop_exec`; vote ≥ 7d; timelock ≥ 48h; one `open_airdrop_id`; merkle `sha256(uint64le account \|\| int64le amount)` with sorted pair hashing; proof ≤ 32; one claim per account; `claimed + amount <= drop.amount`. Fund cannot unstake. After B6, `smartadrop11@active` is `smartastake1@eosio.code` only; `require_auth` would still accept `@owner` as break-glass, but the in-contract novote / proposal-only checks stop unstake/vote/claim.

**Governance bounds** re-checked at execute. `setsplit` hard-codes bucket order `satlp, leeflp, ops, rewards, reserve`. `setlimits` copies live `lock_secs` from the trader config prefix (`begin()` on the singleton-serialized row; integration confirmed lock `1325419200` unchanged against **real** leeftrader wasm after the safe patch). Stake-side caps are tighter than trader's 1..10000 bps.

**Trader patch:** `integration/make_trader_patches.py` still does not touch `leeftrader.cpp`. The naive `name gov` upgrade bricks every `cfg()` read (`datastream`). `binary_extension<name>` plus `setgov("smartastake1")` is required before a passed `setsplit`/`setlimits` can execute (I-2, still a `FINDING` until B5). `has_auth(gov)` matches the inline `permission_level{smartastake1, active}`.

**Freeze:** neither new contract has `pause`. Operational freezes (retire vest/stake admin, `setcode` to `eosio.null`) cannot redirect existing streams or seize user stake. Removing `eosio.code` from the contract `@active` would brick all outbound transfers (claims/withdraws) — do not do that. No on-chain freeze can lock admin out of a still-live guardian/admin key; retiring those keys is an account-permission step.

**Table scans:** stake actions do not iterate `stakes` or `proposals`. Vest has no unbounded walk. CPU DoS via table scan is not a path.

**Inline logs** are `require_auth(self)` so they cannot be spoofed.

## Arithmetic / overflow

- Vesting: `total * elapsed` in `__int128`; `vested <= total`; `claimed` cannot exceed vested; schedule sum checked against uint32.
- Stake: `muldiv` 256-bit; `owed` / `pending` / vote weights checked against `int64` max. SAT max supply 1e12 units (4 dp × 1e8) is far below `int64`.
- Quorum/approval/airdrop cap use `__int128` bps math.
- `unstake_amount += amount` has no extra overflow check; at SAT scale it cannot overflow `int64` given `amount <= s.amount` and the global invariant.
- Accumulator `rpt_hi/lo` as uint128: at 100M SAT rewards and a 1-unit stake, still ~1e30 ≪ 2^128.

## Reentrancy / inline ordering

Antelope has no EVM reentrancy, but nested notifies are real.

- Vest `claim`: `claimed += paid` then inline `transfer`. Double-claim in one tx is tested (`doubleclaim.cpp`); the second hits `nothing to claim` and the tx rolls back.
- Stake `claim`/`withdraw`/`claimdrop`: accounting first, then `send_sat`. Outbound transfer notify returns immediately (`from == self`).
- `execute` of `setsplit`/`setlimits` sends the trader inline **in the same action**; if the trader rejects (no `setgov`), the whole tx reverts and status stays queued (retry until grace).
- `fund_reward` may `compound_into` the fund (no external call except later `logreward`).

No deferred transactions.

## Freeze / admin brick / locked funds

- No `pause` on vest or stake. Claims and withdraws cannot be frozen by an in-contract switch.
- Retiring vest admin stops new streams; existing streams keep paying.
- Retiring stake admin stops `setfunder`; if that happens before B3, the rewards stream is stuck (M-06 / I-1).
- Guardian remains `smartaadmin1` (not votable). Veto cannot seize funds; it only stops a queued/active proposal.
- `assert_invariant` on mutating paths: if it ever failed (`balance < need`), `unstake`/`withdraw`/`claim` would revert for everyone. Review did not find a way for an attacker to desync the books without a token-contract compromise.
- Removing `eosio.code` from contract `active` bricks outbound SAT. Do not freeze that permission.
